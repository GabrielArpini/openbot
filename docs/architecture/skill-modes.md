# Persistent skill modes

A mode is explicit instruction content for one existing public chat. It is not a change to the agent profile or the optional skill catalog. The chat control stores an installed skill ID, revision and SHA-256 hash in `thread_skill_modes`. Agent defaults are stored in `agent_skill_mode_defaults`. A chat with no row inherits the default; a row containing null is explicitly off. `scope: inherit` removes only the chat override. `scope: agent` changes only the default. Agent defaults survive roster projection replacement and are removed when the agent is forgotten. Channels are not configured separately.

`SkillModes` checks chat ownership and resolves the installed source on the host. The renderer can send only identifiers, not a path or body. The source adapter checks enabled state, installation integrity, frontmatter and file containment. It reads through EOF within a byte limit. The domain rejects empty bodies and any final rendered instruction block above 32,000 UTF-16 code units, including labels, metadata, escaping and wrappers. It never truncates a mode. Existing secret redaction remains in effect on provider input.

The lifecycle resolves the source before each turn. A changed revision or hash fails closed until the user selects the current revision or disables the mode. `provider_session_skill_modes` records the selection given to each provider-qualified external session ID. A different selection starts a replacement provider session for that public chat and keeps its stored conversation. A provider switch or process restart reconstructs the text through the same lifecycle.

The complete body is appended to developer instructions and passed separately through `TurnContext` for each ordinary user turn. Slash commands keep their command syntax; the next ordinary turn includes the mode again. Existing provider compaction handling retains or reconstructs developer instructions, and the next ordinary turn always repeats the mode. Provider history filters remove injected mode blocks so old selections do not become visible user messages or handoff text. A provider's internal context during an autonomous mid-turn continuation is not observable as a model guarantee.

Desktop IPC and optional Team API routes use the same host service. `skill-modes-v1` requires owner/admin authority and visible-agent access. Older hosts hide the action. Change events refresh other clients. Desktop main, task and side chat controls, web controls, and native mobile main/task controls share this contract. The control appears after a public chat exists. Optional icon/color decoration is not included.

Verification uses isolated databases, source folders and fake provider processes through real adapters. No provider credentials or customer content are required. Tests check input delivery, not model obedience. Broad builds and mobile typechecks stay in CI under the repository check policy.

An installed package can declare `mode-context.json` with version 1, root `SKILL.md`, and a nodes map. Each package-relative node has SHA-256, a revision string or honest null, and ordered `{path, when}` dependencies. The host resolves only these explicit local edges, never ordinary Markdown links or URLs. It includes root-first bodies once, preserves every applicability edge, and rejects cycles, unreachable entries, missing or changed files, path escapes and overflow. Conditional dependencies are always delivered; their conditions constrain when the model applies them. The effective selection hash covers the complete rendered dependency set, including provenance and conditions. A root without this manifest remains a normal single-skill mode.
